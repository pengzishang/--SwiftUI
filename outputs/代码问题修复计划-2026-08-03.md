## 1. 目标与边界

### 1.1 本轮目标

1. 保证 AI 会话持久化始终满足“最新状态最终落盘”，旧快照不能覆盖新状态。
2. 让首页 Feed 消费者终止时，底层 producer、网络请求和后续缓存副作用同步停止。
3. 用带命名空间、明确可访问性、可靠错误传播和兼容迁移的 Keychain 存储替代通用 helper。
4. 让现有 OAuth 实现和测试真正参与编译与回归，但不启用尚未获批准的生产登录。
5. 消除 `HTTPClient` 并发复用单个可变 `JSONDecoder` 的不明确契约。
6. 每项修复都具备针对性自动化测试、独立提交和可回滚边界。

### 1.2 明确非目标

以下内容本轮不修改：

- P1-1：内置 AI Provider 配置及 API Key 进入客户端 Bundle 的现状；
- `Config/AIProviders.xcconfig`；
- `Config/AIProviders.local.xcconfig.example`；
- `DailyReader/Resources/Info.plist` 中的 `AIBuiltInProviders`；
- `DailyReader/Features/AI/AIBuiltInProviderLoader.swift`；
- `AppEnvironment.makeAIChatCoordinator()` 的内置 Provider 安装流程；
- 真实知乎 OAuth client ID、endpoint、scope、redirect URI、URL Scheme 或 Associated Domains；
- 真实授权页面启动、token 交换、profile 请求和生产账号登录；
- 与五项问题无关的 UI 重设计、缓存策略改造或网络层重构。

> P1-1 是用户明确接受的剩余风险。本计划只保证不扩大它，不把它混入其他修复，也不把“未修”误写成“已解决”。

## 2. 总体技术决策

| 问题 | 决策 | 正确性来源 |
|---|---|---|
| P1-2 | 在 `AISessionStore` actor 内实施单调 revision 与写入合并；外层 Task 取消只用于节流 | actor 内拒绝过期 revision，而非依赖任务调度顺序 |
| P2-1 | `onTermination` 取消 producer；网络及缓存副作用前后检查取消 | 消费者生命周期成为 producer 生命周期的唯一所有者 |

| P3-1 | `HTTPClient` 注入 decoder factory，每个请求创建独立 decoder | 不在并发请求之间共享 `JSONDecoder` 实例 |
| P2-3 | OAuth 源码、单测、UI 测试纳入现有 targets；普通运行固定 unavailable，只有 `-UITestMode` 可使用 fixture | 编译覆盖与产品开关分离，默认失败关闭，不存在隐式生产入口 |

## 5. 阶段 1：修复 P1-2 AI 会话持久化顺序

### 5.1 设计

为每个持久化请求分配单调递增 revision：

```swift
struct AISessionSnapshot: Sendable {
    let revision: UInt64
    let sessions: [AIChatSession]
}
```

`AIChatCoordinator` 负责生成 revision；`AISessionStore` actor 负责决定哪个 revision 可以落盘：

- `persist()` 在主 actor 上获取不可变快照并递增 revision；
- store 记录 `latestRequestedRevision` 和 `latestCommittedRevision`；
- 小于最新已见 revision 的请求直接丢弃；
- actor 内合并短时间内的连续请求，减少流式 delta 引起的写放大；
- 真正写文件前再次核对 revision；
- 即使旧外层 Task 晚于新 Task 进入 actor，旧 revision 也不能覆盖新文件；
- 删除会话产生的空数组同样是合法快照，不能被旧的非空快照恢复；
- 保留 `.atomic` 写入与现有 schema 兼容读取。

外层 `persistenceTask?.cancel()` 可以保留为性能优化，但不再承担数据正确性；任何正确性测试都不得依赖 `Task.yield()` 的偶然调度。

### 5.2 预计修改文件

- `DailyReader/Features/AI/AIChatCoordinator.swift`
  - 增加 revision 状态；
  - 将 `persist()` 改为提交带 revision 的快照；
  - 保持 `@MainActor` 状态所有权。
- `DailyReader/Features/AI/AIStores.swift`
  - 扩展 `AISessionStore` 的 revision/合并语义；
  - 为测试注入可控写入器或提交挂点；
  - 保留现有 legacy 日期解码与 streaming→interrupted 恢复逻辑。
- `DailyReaderTests/AISessionStoreTests.swift`
  - 增加 store 级顺序和最终磁盘状态测试。
- `DailyReaderTests/AIChatViewModelTests.swift` 或新建 `AIChatCoordinatorPersistenceTests.swift`
  - 增加 coordinator 级连续更新测试。

### 5.3 必测场景

1. revision 2 先进入 store、revision 1 后到达，最终文件仍为 revision 2。
2. revision 1 正在排队时 revision 2 到达，最终文件为 revision 2。
3. 连续多次流式 delta 后，磁盘消息内容等于最后一次完整内容。
4. 重命名后紧接消息更新，标题和消息均为最新状态。
5. 删除会话后旧保存请求晚到，已删除会话不恢复。
6. 所有会话删除后，磁盘允许保存空列表。
7. 原有 round-trip、legacy 解码和中断消息恢复测试继续通过。

### 5.4 验收标准

- 最终磁盘快照严格等于最高 revision 对应快照。
- 测试使用可控挂点制造倒序，不使用固定 sleep 猜时序。
- 高频更新被合并，写次数小于请求次数；但应用主动 flush 后最新数据已落盘。
- 不改变 `AIChatSession` 对外模型和现有会话文件 schema，或在必要变更时提供向后兼容解码。

## 6. 阶段 2：修复 P2-1 首页 Feed 取消传播

### 6.1 设计

`loadHomeFeed()` 创建 producer 后立即把其所有权交给 stream continuation：

```swift
let producer = Task { await self.streamHomeFeed(to: continuation) }
continuation.onTermination = { @Sendable _ in
    producer.cancel()
}
```

`streamHomeFeed` 的取消规则：

- 读取缓存后、yield 前检查取消；
- 网络请求前后检查取消；
- `saveLatest`、`saveHomeFeed` 前检查取消；
- `CancellationError` 单独处理，不降级为“离线但有缓存”的正常结束；
- `yield` 返回 `.terminated` 后立即停止；
- continuation 只完成一次；消费者离开后不得继续产生缓存副作用。

### 6.2 预计修改文件

- `DailyReader/Repositories/DailyRepository.swift`
- `DailyReaderTests/DailyRepositoryTests.swift`
- 必要时调整测试支持中的 `RepositoryMockDailyService` 与 `RepositoryInMemoryCacheStore`，增加取消和写入观测。

### 6.3 必测场景

1. 消费者取得首个缓存事件后结束迭代，service 中悬挂的 `fetchLatest()` 收到取消。
2. 消费者在无缓存网络等待阶段被取消，producer 结束且不写 `latest/homeFeed` 缓存。
3. 网络已经返回但取消发生在缓存写入前，后续副作用被跳过。
4. 正常 cache→network 事件顺序保持不变。
5. 无缓存且普通网络失败时仍抛原有 `APIError`，不能被误判为取消。
6. 有缓存且普通网络失败时仍保留原有离线降级行为。

### 6.4 验收标准

- stream 终止后 producer 不再存活。
- 取消沿调用链保持为取消语义，而不是普通业务错误。
- 取消后没有新的缓存写入或 refreshed 事件。
- 现有首页加载与失败降级测试无回归。

### 6.5 回滚点

独立提交建议：`fix: 传播首页 Feed 流取消`。

## 7. 阶段 3：修复 P2-2 Keychain 命名空间、错误和迁移

### 7.1 共享底层抽象

把当前位于 OAuth 文件中的通用 SecItem 能力提取到 Storage 层，例如：

- `DailyReader/Storage/KeychainSecItemClient.swift`
  - `KeychainSecItemClient`
  - `SystemKeychainSecItemClient`
  - `KeychainStoreError.status(OSStatus)`
- `DailyReader/Storage/KeychainDataStore.swift`
  - 初始化时固定 `service`；
  - 每次操作指定 `account`；
  - `read/save/delete` 均为 throwing；
  - 新增项明确使用 `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`；
  - 明确 `kSecAttrSynchronizable = false`；
  - 只把 `errSecItemNotFound` 解释为无数据；
  - update→not found→add；其余状态原样抛出；
  - delete 只接受 success/not found。

建议命名空间：

| 数据 | service | account |
|---|---|---|
| 阅读状态备份 | `com.codex.DailyReader.reading-state.v1` | 保留现有四个业务 key 作为 account |
| AI Provider 凭据 | `com.codex.DailyReader.ai-credentials.v1` | 保留 `DailyReader.ai.provider.<providerID>` |
| OAuth Session | `com.codex.DailyReader.auth.zhihu.oauth.v1` | `session.current` |

不同 service 保证删除 OAuth session 不可能命中阅读状态或 AI 凭据。

### 7.2 兼容迁移

现有数据由“只有 account、没有显式 service”的旧 helper 写入。迁移必须执行：

1. 先读取新命名空间；存在则直接返回，绝不触碰 legacy。
2. 新项不存在时，查询 legacy 候选并请求 attributes、data 与 persistent reference。
3. 如果没有候选，返回 nil。
4. 如果存在多个无法唯一识别的候选，报迁移歧义；不得猜测或批量删除。
5. 将 legacy data 写入新 service/account。
6. 从新项回读并逐字节验证。
7. 仅在验证成功后，通过 captured persistent reference 精确删除旧项。
8. 新写入、回读或删除失败时上抛；若复制未验证成功，旧项必须保留。
9. 迁移应幂等：中断后再次运行不会丢失或重复破坏数据。

AI 现有 `DailyReader.ai.apiKey` → provider account 的二级业务迁移继续保留，但底层迁移先完成，且每一步都使用 throwing API。

### 7.3 调用方策略

- `AIKeychainCredentialStore`：直接传播 Keychain 错误，移除“写后回读才推断失败”的做法；保留 UTF-8 编码错误。
- `HomeViewModel`：通过注入的阅读状态备份 store 使用 Keychain；UserDefaults 仍是当前本地状态来源，Keychain 作为备份。Keychain 失败不应让阅读功能崩溃，但必须进入脱敏日志/可测试错误报告入口，不能静默当作“没有数据”。
- 对损坏备份：只有确认是数据解码损坏时才精确删除对应 namespaced item；权限或交互错误不得触发删除。
- UI 测试中的 corrupted 场景改由可注入 double 驱动，不再依赖真实 Keychain 的模糊行为。

### 7.4 预计修改文件

- 新增 `DailyReader/Storage/KeychainSecItemClient.swift`
- 新增 `DailyReader/Storage/KeychainDataStore.swift`
- 修改或移除 `DailyReader/Storage/KeychainHelper.swift`
- `DailyReader/Features/AI/AIStores.swift`
- `DailyReader/Features/Home/HomeViewModel.swift`
- `DailyReader/Authentication/OAuthSessionStore.swift`

### 7.5 必测场景

1. add 查询包含准确 service/account、device-only accessibility、non-synchronizable。
2. update 成功时不 add；update 返回 not found 时 add。
3. copy/add/update/delete 的非预期 `OSStatus` 均被上抛。
4. 只有 `errSecItemNotFound` 返回 nil。
5. namespaced item 优先于 legacy，不删除 legacy 同名候选。
6. legacy 单候选迁移成功后新项可回读，并通过 persistent ref 精确删除旧项。
7. 新项写入失败、验证不一致或 legacy 删除失败时行为可观测，且不会在复制成功前丢失旧数据。
8. 多个 legacy 候选时拒绝迁移，不进行广泛删除。

11. HomeViewModel 在 Keychain 失败时仍可使用 UserDefaults，并产生脱敏错误记录。

## 8. 阶段 4：修复 P3-1 JSONDecoder 并发复用

### 8.1 设计

将单个 decoder 实例改为工厂：

```swift
typealias JSONDecoderFactory = @Sendable () -> JSONDecoder

init(
    session: URLSession = .shared,
    decoderFactory: @escaping JSONDecoderFactory = { JSONDecoder() },
    timeoutInterval: TimeInterval = 15
)
```

每次 `execute` 调用 `decoderFactory()`，把独立实例传给 Alamofire。项目当前没有生产调用方注入自定义 decoder，因此可以直接收紧 API；测试补充自定义 date/key strategy，保证可配置性没有丢失。

不采用全局锁或 actor 串行化解码，因为这会无谓降低历史日报并发收益。

### 8.2 预计修改文件

- `DailyReader/Networking/HTTPClient.swift`
- `DailyReaderTests/HTTPClientTests.swift`
- 必要时更新直接构造 `HTTPClient` 的测试辅助代码。

### 8.3 必测场景

1. 单次请求仍保持 URL、Header、状态码和错误映射行为。
2. 自定义 decoder factory 的日期/key strategy 生效。
3. 多个并发请求各自调用 factory，并取得不同 decoder 实例。
4. 并发成功与解码失败能分别映射，不因共享状态互相污染。
5. 历史日报 task group 的并发度不下降。

### 8.4 验收标准

- `HTTPClient` 不再持有共享 `JSONDecoder`。
- factory 每个请求恰好调用一次。
- 现有 `APIError` 映射不变。
- 不通过锁将全部响应解码串行化。

### 8.5 回滚点

独立提交建议：`refactor: 为每个网络请求创建 Decoder`。

## 9. 阶段 5：修复 P2-3 OAuth target 与测试治理

### 9.1 最终范围决策

选择“纳入现有 App/Test targets，但默认关闭生产能力”，而不是继续排除或新增一个长期无人运行的 experimental target。

这样可以同时满足：

- 所有 OAuth 安全代码参与日常编译；
- 所有 OAuth 单元测试参与默认 Scheme；
- fixture UI 流程得到回归保护；
- 普通 Debug/Release 启动不能构造或启动真实授权；
- 没有官方参数时，用户只看到明确的“暂不可用”状态。

### 9.2 服务选择规则

提取可测试的 authentication factory/launch context，选择规则必须严格如下：

| 启动条件 | 服务 | 是否可发真实认证流量 |
|---|---|---|
| 普通 Debug | `UnavailableAuthenticationService(.missingRequiredValues)` | 否 |
| 普通 Release | `UnavailableAuthenticationService(.missingRequiredValues)` | 否 |
| `-UITestMode` + mock scenario | `FixtureAuthenticationService` | 否 |
| 仅设置 `MOCK_AUTH_SCENARIO`、没有 `-UITestMode` | Unavailable | 否 |
| 未来官方配置获批 | 不在本计划内；需独立评审后显式新增 Production 分支 | 本轮否 |

本轮禁止在普通启动路径调用 `BundleAuthenticationConfigurationLoader` 后自动选择 production。即使本机或 Info.plist 意外存在看似完整的值，也必须保持 unavailable，防止“配置漂入即上线”。

### 9.3 App/UI 接线

- `AppRootView` 用 `@StateObject` 在 App 生命周期内持有一个 `AuthenticationViewModel`。
- `AppEnvironment` 通过严格 launch gate 构造 unavailable 或 fixture service。
- `MeView` 接收 authentication view model，并在现有书房内容上方展示 `AccountCardView`。
- 普通启动显示禁用的“知乎登录暂不可用”；不能点击、不能打开网页。
- `-UITestMode` 下才展示可交互 fixture 状态，现有收藏、已读、搜索、设置功能必须保留。
- 视图退出时取消正在运行的 fixture/auth view-model task。

### 9.4 XcodeGen 修改

修改 `project.yml`：

- App target 不再排除 `Authentication`；
- App target 不再排除 `Features/Me/AccountCardView.swift`；
- App target 不再排除 `Features/Me/AuthenticationViewModel.swift`；
- 保留 `Features/Settings/SettingsView.swift` 的排除，因为仓库另有同名 `Features/Home/SettingsView.swift`，该项与 OAuth 无关；
- Unit Test target 移除 8 个 Authentication/OAuth/PKCE excludes；
- UI Test target 移除 `AuthenticationFlowUITests.swift` exclude；
- 运行 `xcodegen generate` 并审查 `.pbxproj`；
- 再次生成必须无额外 diff，证明配置幂等。

本轮 `project.yml` 不新增：

- `ZHIHU_OAUTH_*` Info.plist 属性；
- URL Types / callback scheme；
- Associated Domains；

### 9.6 必测场景

#### Target/编译治理

1. 10 个 Authentication 源文件均出现在 App target compile sources。
2. 8 个相关单测文件均进入 `DailyReaderTests`。
3. `AuthenticationFlowUITests.swift` 进入 `DailyReaderUITests`。
4. 配置检查测试或脚本在关键测试再次被 excludes 时失败。

#### 默认关闭

1. 普通 launch context 总是产生 unavailable service。
2. 未带 `-UITestMode` 时，`MOCK_AUTH_SCENARIO` 被忽略。
3. 意外存在 Bundle OAuth 值时，本轮 factory 仍不构造 production service。
4. unavailable 按钮存在但 disabled。
5. 不创建 `ASWebAuthenticationSession`，不发送 token/profile 请求。

#### Fixture/UI

1. success、denied、cancelled、retry、restore、expired、invalid callback、avatar failure、sign-out 等现有场景通过。
2. fixture 测试没有 web view/外部授权页面。
3. Me 页收藏、已读、搜索、设置入口仍可使用。
4. Account card 在 iPhone/iPad 和大字体下不遮挡主要内容，交互目标不小于 44pt。
5. 退出登录只影响 fixture auth session，不删除本地阅读数据。

#### 安全隔离

1. OAuth HTTP client 仍与公共 `HTTPClient` 隔离。
2. OAuth bearer token 不会进入日报、热榜、详情请求。
3. OAuth Keychain service 与阅读状态、AI 凭据不同。
4. 仓库和构建产物中不新增 confidential client secret。

### 9.7 验收标准

- OAuth 代码和测试不再被默认 target 排除。
- 默认 Scheme 能编译并执行所有相关测试。
- 普通 App 启动只能处于 unavailable 状态。
- 只有同时存在 `-UITestMode` 和受支持 mock scenario 时才允许 fixture 可交互。
- 本轮没有任何真实 OAuth 配置、callback 注册或生产网络能力。
- 若因纳入 target 暴露编译错误，必须修复后再视为完成，不能重新 excludes 掩盖。

### 9.8 回滚点

1. `build: 将 OAuth 模块纳入默认 targets`

回滚不得通过重新排除安全测试来制造“绿灯”；若暂时关闭 UI，应保留源码和单测编译覆盖。

## 12. 风险登记

| 风险 | 控制措施 |
|---|---|
| revision 只在 coordinator 生效，store 仍可被其他调用方绕过 | revision 校验放在 store actor；旧无 revision save API 收紧或仅供测试兼容 |
| cancellation 被 catch 当普通失败 | 单独匹配 `CancellationError`，并测试无缓存/有缓存两条路径 |
| Keychain 迁移删除错误项 | 使用 persistent ref 精确删除；复制验证前绝不删除；多候选拒绝猜测 |
| HomeViewModel 同步初始化难以使用 actor store | 使用同步 throwing 的 SecItem wrapper，并通过注入与错误报告保持可测试性；不在主线程做网络或长任务 |
| OAuth 纳入 target 后意外上线 | factory 普通路径硬编码 unavailable；不读取生产配置；不注册 callback；加负向测试 |
| OAuth 文件暴露历史编译错误 | 正面修复并保留测试，禁止重新 excludes |
| Account card 改变 Me 页首屏布局 | 使用现有 720pt 宽度约束和自适应布局，补 iPhone/iPad/大字体 UI 回归 |
| decoder factory 被错误实现为返回同一实例 | 并发测试记录实例身份/创建次数，要求每请求新建 |
| 当前环境无法运行完整测试 | 如实标记阻塞，在合并前于正常 Xcode 环境补跑，不以静态审查冒充通过 |

## 13. 执行结论

本计划优先修复可能造成用户数据回退的 P1-2，然后处理生命周期取消、Keychain 数据安全、decoder 并发契约，最后完成依赖共享 Keychain 抽象的 OAuth target 治理。OAuth 的修复目标是“让代码和测试活起来”，不是“让生产登录上线”；普通运行保持明确、可验证的 unavailable 状态，直到官方合同、callback 和配置经过独立批准与安全评审。
