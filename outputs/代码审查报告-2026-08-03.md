## P1 — 高严重度

### P1-1 内置 AI API Key 被编译进 `Info.plist`，可从 IPA 提取

**证据**

- `project.yml:25-27,39`：Debug/Release 均使用 `Config/AIProviders.xcconfig`，并把 `$(AI_BUILTIN_PROVIDERS_B64URL)` 写入 `AIBuiltInProviders`。
- `Config/AIProviders.local.xcconfig.example:1-4`：示例 payload 明确包含 `apiKey`，仅做 Base64URL 编码。
- `DailyReader/Resources/Info.plist:5-6`：最终 plist 字段直接引用该构建变量。
- `DailyReader/Features/AI/AIBuiltInProviderLoader.swift:25-38,54-68`：运行时从主 Bundle 读取、解码，并得到明文 Key。
- `DailyReader/AppRootView.swift:143-150`：启动后把内置 Key 写入 Keychain；但这无法撤销 Key 已存在于应用包中的事实。

**触发条件**

只要 Release 构建时配置了真实 `AI_BUILTIN_PROVIDERS_B64URL` 并分发应用，任何能获得 IPA/App Bundle 的人都可以读取 plist、Base64URL 解码并得到全部 endpoint、model 和 API Key。

**影响**

- 凭据泄露、额度盗用和账单风险；
- 供应商侧滥用可能关联到项目账号；
- Keychain 仅保护运行时副本，不能保护 Bundle 内原始副本。

**修复方向**

- 客户端只携带非敏感服务标识，不携带长期供应商 Key；
- 通过自有 BFF/令牌代理完成供应商请求，客户端取得短期、受限、可撤销令牌；
- 若必须客户端直连，让用户自行配置个人 Key；
- 立即轮换任何曾打入可分发构建的 Key，并增加产物扫描门禁（对 `.app/Info.plist` 和字符串表扫描）。

**置信度：高**

### P1-2 会话持久化存在旧快照覆盖新状态的竞争

**证据**

- `DailyReader/Features/AI/AIChatCoordinator.swift:186-194`：每次状态变化先 `persistenceTask?.cancel()`，再创建新 Task；Task 内只在进入 `sessionStore.save` 前检查一次取消。
- `DailyReader/Features/AI/AIStores.swift:87,136-140`：`AISessionStore` 是 actor，`save` 内没有取消检查，直接原子写文件。
- 流式响应每个 delta 都会调用 `coordinator.update(session)`（`AIChatCoordinator.swift:344-363`），因此会高频创建/取消写任务。

**触发条件**

旧持久化任务通过 `guard !Task.isCancelled` 后，正在等待 `AISessionStore` actor；此时新状态触发取消旧任务并排入新保存。actor 消息的执行顺序与外层 Task 的期望“最后写入获胜”并无版本保证，旧快照仍可能在新快照之后落盘。

**影响**

应用被终止或下次启动时，可能恢复到较旧的消息内容、旧标题、旧草稿，甚至把刚删除的会话恢复出来。

**修复方向**

- 把“最新快照获胜”放进同一个 actor：保存请求携带单调递增 revision，actor 仅写入不小于已见 revision 的快照；或 actor 内实现 debounce/coalescing；
- 在真正写盘前再次检查取消，但不要把它作为唯一正确性保障；
- 对删除、重命名、连续流式 delta 增加“最终磁盘快照必须等于最新内存快照”的并发测试。

**置信度：中高**

## P2 — 中严重度

### P2-1 首页 Feed 的 `AsyncThrowingStream` 不传播消费者取消

**证据**

- `DailyReader/Repositories/DailyRepository.swift:21-26`：创建无结构 `Task` 执行 `streamHomeFeed`，但没有保存 Task，也没有设置 `continuation.onTermination`。
- `DailyReader/Repositories/DailyRepository.swift:130-164`：底层会读写缓存并请求最新日报。
- 对比项目内更完整的做法：`AIChatService.swift:28-57` 明确在流终止时 `task.cancel()`。

**触发条件**

`HomeView.task` 因视图离开或场景变化被取消，`for try await` 消费停止，但 Repository 内创建的 Task 不会随之取消。

**影响**

- 已无消费者的网络请求和缓存写入继续执行；
- 反复创建/销毁视图时可能出现重复请求；
- 增加电量、流量和后台工作，且测试无法观察正确的取消语义。

**修复方向**

创建 producer Task 后，在 `continuation.onTermination` 中取消；`streamHomeFeed` 在网络和写缓存前后检查取消，并避免把取消映射为普通网络失败。

**测试缺口**

`DailyRepositoryTests.swift` 覆盖 cache/network 顺序和错误降级，但没有“消费者取消后 service 收到取消、且不再写缓存”的测试。

**置信度：高**

### P2-2 通用 Keychain helper 缺少 service 命名空间、可访问性策略并吞掉错误

**证据**

- `DailyReader/Storage/KeychainHelper.swift:10-50`：查询只包含 `kSecClass` + `kSecAttrAccount`，没有 `kSecAttrService`；新增项没有 `kSecAttrAccessible`；所有 SecItem 返回状态都被忽略或折叠为 nil。
- 它被用于用户阅读状态备份和 AI Key（`HomeViewModel.swift:76-180,355-449`；`AIStores.swift:55-84`）。
- 同仓库已有更安全实现：`OAuthSessionStore.swift:32-99` 使用 service/account、明确 accessible 策略并抛出 OSStatus。

**触发条件**

同一 App/访问组内出现同 account 的其他 generic-password 项，或设备 Keychain 返回交互受限、权限、重复项、写入失败等状态。

**影响**

- 可能读写/删除错误条目；
- 失败被当成“没有数据”，迁移代码可能删除或覆盖原数据；
- AI Key 保存失败只靠回读间接发现，其他阅读状态写入则完全静默失败；
- 默认 Keychain 可访问性不明确，不利于安全审计。

**修复方向**

统一改为带 `service + account` 的 throwing store，显式使用合适的 `kSecAttrAccessible`（例如 `AfterFirstUnlockThisDeviceOnly` 或按产品需求更严格），只把 `errSecItemNotFound` 当成 nil；其他状态必须上抛/记录脱敏错误。可以复用 `OAuthSessionStore` 的客户端抽象和测试方式。

**置信度：高**

### P2-3 OAuth 生产实现和全部相关测试未编入任何 target

**证据**

- `project.yml:17-21`：App target 排除整个 `DailyReader/Authentication`、`AccountCardView.swift`、`AuthenticationViewModel.swift` 和另一个 Settings 文件。
- `project.yml:51-59`：单元测试 target 排除 Authentication/OAuth/PKCE 全部测试。
- `project.yml:71-72`：UI 测试 target 排除 `AuthenticationFlowUITests.swift`。
- 当前 `.pbxproj` 中检索不到这些文件，说明生成工程与该配置一致。
- `docs/features/zhihu-login/architecture.md:3,727-744` 说明真实 provider 集成仍被官方配置阻塞，因此这更像“已实现但刻意禁用”的模块，而不是当前线上功能突然失效。

**触发条件**

团队误以为这些已存在的 Swift/XCTest 文件参与编译或回归测试，或者后续修改 OAuth 代码但只运行默认 Scheme。

**影响**

- 代码可长期腐化而 CI 全绿；
- 编译错误、并发问题、安全回归不会被发现；
- 文档、源码和实际产品能力容易产生错觉。

**修复方向**

二选一并明确化：

1. **正式接入**：补齐官方配置后，将生产代码、UI 和测试纳入 targets，并执行文档中的完整门禁；
2. **保持阻塞**：将实现隔离到独立 experimental target/package，或删除未启用实现，仅保留设计文档；CI 增加“禁止关键安全测试被 excludes”的配置检查。

**置信度：高**

## P3 — 低严重度 / 可维护性

### P3-1 `HTTPClient` 复用单个 `JSONDecoder` 进行并发解码，线程安全契约不明确

**证据**

- `DailyReader/Networking/HTTPClient.swift:4-8,35`：单例客户端持有一个可变引用类型 `JSONDecoder`，所有请求复用。
- `DailyRepository.swift:286-310`：历史日报通过 task group 并发调用同一 service/client。

**影响**

Foundation 没有在该代码中建立“共享 decoder 可安全并发调用”的项目级保证；即使当前运行通常正常，也让严格并发审计和后续添加自定义 decoding strategy/userInfo 更脆弱。

**修复方向**

注入 decoder factory 或每次请求创建/复制配置后的 decoder；如果坚持共享，至少通过 actor/锁串行化解码并增加并发压力测试。优先级低于前述数据和安全问题。

**置信度：中**
